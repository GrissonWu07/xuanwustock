# 量化股票生命周期与自动入池流程说明

本文说明当前系统中“发现股票 / 研究股票”如何进入实时量化，以及进入量化后的生命周期如何运转。本文以当前代码实现为准，用于产品使用、排查问题和后续开发对齐。

## 1. 总体结论

发现页和研究页不再只是结果展示页。任务执行完成后，系统会把明确落到股票代码的结果自动写入统一股票池，并生成量化候选事件。

是否进一步进入实时量化，由系统级开关 `auto_entry_mode` 决定：

| 模式 | 行为 |
|---|---|
| `manual_only` | 自动写入股票池和候选事件，但不标记 eligible，也不进入量化。 |
| `confirm_first` | 自动写入股票池和候选事件；候选评分达标后标记为 `eligible`，需要用户一键确认进入量化。默认模式。 |
| `auto_trial` | 自动写入股票池和候选事件；候选评分达标且未被风控阻断时，自动进入量化。 |

这个开关不放在实时模拟页，而是放在：

```text
/settings -> 量化策略自动化
```

该区块提供三个系统级控制：

1. `量化生命周期`：控制候选事件聚合、自动状态推进和自动恢复链路是否启用。
2. `自动入池模式`：控制发现 / 研究结果进入量化的方式。
3. `自动出池`：控制是否根据健康度把股票自动转入只出场、冷却或退出。

实时模拟页只展示当前读取到的运行口径，不负责修改这些系统级开关。不同策略模型的阈值、容量、仓位倍率仍在策略配置页按 aggressive / stable / conservative 分开设置。

实时模拟主扫描只扫描：

```text
quant_status in ('trial', 'active', 'exit_only')
```

历史回放启动时记录任务股票范围快照：

```text
quant_enabled = 1
```

这里的快照只是一份本次回放要处理的股票代码清单，不会阻塞或改写实时模拟。历史回放使用独立的信号表、交易表和账户表；实时模拟继续按当前股票池和调度配置运行。

因此，`cooling` 状态虽然 `quant_enabled=1`，但不参与实时模拟 10 分钟主扫描；历史回放只会在任务启动时记录当时 `quant_enabled=1` 的股票清单，后续股票池变化不影响已经启动的回放任务。

## 2. 入口来源

当前会进入生命周期系统的来源包括：

1. 发现页 `/discover`
   - AI 扫描
   - 主力选股
   - 低价擒牛
   - 小市值
   - 净利增长
   - 低估值

2. 研究页 `/research`
   - 智策板块
   - 智瞰龙虎
   - 新闻流量
   - 宏观分析
   - 宏观周期中能明确输出股票代码的结果

3. 手工入口
   - 用户手工加入股票池
   - 用户手工执行“纳入量化”
   - 用户手工恢复冷却 / 暂停 / 退出的股票

注意：自动入池发生在发现任务或研究任务执行完成后。仅打开已有结果页面，不会对旧缓存结果重新补写候选事件。

## 3. 发现 / 研究任务完成后的自动处理

### 3.1 数据写入顺序

发现任务或研究任务完成后，系统按以下顺序处理每一只股票：

1. 读取任务输出表中的股票代码、名称、行业、价格、来源、理由。
2. 规范化股票代码。
3. 如果该股票已经在 `trial / active / exit_only`，跳过重复候选事件写入。
4. 写入或更新 `stock_universe`：
   - `watched = 1`
   - `stock_name`
   - `source`
   - `latest_price`
   - `metadata.industry`
   - `metadata.entry_source_type`
   - `metadata.entry_source_key`
5. 生成候选事件 `stock_universe_candidate_events`。
6. 根据 `auto_entry_mode` 决定是否评估 eligible 或自动进入量化。

### 3.2 基础信息缺失判定

如果任务结果里只有代码，没有有效名称和行业，系统会把该股票标记为：

```text
basic_info_missing = true
```

这种股票可以记录候选事件，但不会直接自动进入量化。需要后续基础信息补齐后再进入量化。

如果后续发现 / 研究结果补上了名称或行业，系统允许把旧的 `basic_info_missing` 清掉。

## 4. 候选事件

候选事件表为：

```text
stock_universe_candidate_events
```

候选事件表示“某个来源认为这只股票值得进入量化关注”，但不等于已经进入实时量化。

核心字段：

| 字段 | 说明 |
|---|---|
| `stock_code` | 股票代码 |
| `source_type` | 来源类型，例如 `discover`、`research`、`manual` |
| `source_key` | 具体策略或模块，例如 `main_force`、`low_price_bull` |
| `source_score` | 来源评分，范围 0 到 1 |
| `confidence` | 置信度，范围 0 到 1 |
| `trend` | 趋势方向，通常为 `up / neutral / down` |
| `reason_text` | 来源理由 |
| `status` | `active / eligible / consumed / ignored` 等 |

## 5. 默认来源评分

不是所有发现 / 研究结果都会天然带评分。当前系统会先在发现边界归一化生命周期输入，确保有证据的结果能进入候选评分流程。

系统不再按 `discover / research / low_price / main_force` 等来源默认给分。

如果策略结果明确提供了 `source_score / score / scanner_score / confidence`，系统才使用这些显式推荐字段。若数值是 0 到 100，会自动归一化到 0 到 1。

如果没有显式评分，系统只会从可衡量证据推导分值和置信度，例如结果排序、行情字段完整度、成交额 / 量比、MA / MACD / RSI、策略数值字段等。只有来源名称、展示文案或策略名时，`source_score` 和 `confidence` 会保持 0，并在 `lifecycle_score_diagnostics.reason_code` 中标记 `insufficient_measurable_evidence`。

AI 选股会保留 `scanner_score / technical_score / theme_score / technical_reasons` 等结构化字段；技术确认来自结构化 `technical_reasons` 和技术字段，不解析展示用 `reason` 文本。

趋势字段如果没有明确给出，默认按 `neutral` 处理。发现来源本身只说明“从哪里发现”，不能自动推导为上行趋势。

## 6. 候选评分如何计算

生命周期管理器会聚合同一股票的 `active` 和 `eligible` 候选事件，计算 `candidate_score`。

计算逻辑：

```text
candidate_score =
  recommendation_score_component * recommendation_score_weight
+ confidence_component * confidence_weight
+ trend_component * trend_weight
+ strong_recommendation_bonus * strong_recommendation_weight
+ manual_priority_bonus
- liquidity_penalty
- cooldown_penalty
```

其中：

| 组件 | 说明 |
|---|---|
| `recommendation_score_component` | 候选事件明确提供的最高推荐分；来源名称不参与加分 |
| `confidence_component` | 候选事件明确提供的最高置信度 |
| `trend_component` | 明确趋势分，未提供时为中性 |
| `strong_recommendation_bonus` | 推荐分、置信度、趋势同时较强时加分 |
| `manual_priority_bonus` | 手工来源加优先权 |
| `liquidity_penalty` | 流动性不足扣分 |
| `cooldown_penalty` | 冷却期扣分 |

评分最终会限制在 0 到 1。

`source_type`、来源名称和同一股票被多少来源发现，只能用于展示、审计、容量限制和去重，不进入候选分。

## 7. 不同策略 profile 的准入差异

生命周期参数跟随策略 profile，而不是固定一套规则。

| 参数 | aggressive | stable | conservative |
|---|---:|---:|---:|
| `trial_threshold` | 0.50 | 0.55 | 0.65 |
| `strong_candidate_threshold` | 0.70 | 0.75 | 0.82 |
| `high_reentry_threshold` | 0.85 | 0.88 | 0.92 |
| 每批自动纳入上限 | 6 | 4 | 2 |
| 每日自动纳入上限 | 20 | 12 | 6 |
| 单策略每批自动纳入上限 | 3 | 2 | 1 |
| 同行业每日自动纳入上限 | 3 | 2 | 1 |

含义：

1. aggressive 更容易进入 trial，自动纳入数量也更多。
2. stable 是中性默认。
3. conservative 要求更高，自动纳入更少。

## 8. 什么时候可以进入量化

### 8.1 进入 eligible

在 `confirm_first` 或 `auto_trial` 模式下，股票会先经过候选评分。

进入 `eligible` 的条件：

1. 生命周期开关 `quant_universe_lifecycle_enabled = true`
2. 股票不在量化、正常扫描或只出场管理中
3. 股票未被 `manual_ban`
4. 股票不是停牌、涨停、跌停等不可交易状态
5. 股票不在有效冷却期 `cooling_until`
6. 如果是 `retired` 重新入池，评分要达到 `high_reentry_threshold`
7. `candidate_score >= trial_threshold`

进入 eligible 后：

```text
stock_universe_candidate_events.status = 'eligible'
```

UI 上显示：

```text
eligible
```

### 8.2 自动进入量化

只有 `auto_entry_mode = auto_trial` 时，eligible 股票才会自动进入量化。内部状态值仍为 `trial`，UI 一律显示“量化”。

自动进入量化的额外条件：

1. 不是 `basic_info_missing`
2. 未超过当日自动纳入总量上限
3. 手工批量纳入时，还会检查批次容量、单策略容量、行业容量、概念容量

自动进入量化后会写：

```text
stock_universe.quant_status = 'trial'
stock_universe.quant_enabled = 1
stock_universe_quant_state.candidate_score = 当前候选评分
stock_universe_quant_events.event_type = 'candidate_promoted_to_trial'
stock_universe_candidate_events.status = 'consumed'
```

UI 上显示：

```text
already_in_quant
```

### 8.3 只记录候选事件但不进入量化

以下情况不会进入量化：

| 原因 | UI / 事件表现 |
|---|---|
| `auto_entry_mode = manual_only` | 只写 active 候选事件，不自动 eligible / 量化 |
| `auto_entry_mode = confirm_first` | 达标后只显示 eligible，等待用户确认 |
| 分数低于 `trial_threshold` | skipped / below_trial_threshold |
| 基础信息严重缺失 | eligible 但不会 auto_trial |
| 冷却期未结束 | cooling_blocked |
| 手工禁止 | manual_ban |
| 不可交易 | non_tradable |
| retired 复活分数不足 | retired_reentry_below_threshold |
| 每日自动纳入容量已满 | eligible / daily_capacity_exceeded |

## 9. 手工纳入量化

用户可以在 UI 中对 eligible 股票执行“纳入量化”。

API：

```text
POST /api/v1/quant/universe/actions/promote-to-trial
```

请求：

```json
{
  "stock_codes": ["600519", "300750"],
  "source_type": "discover",
  "source_key": "main_force"
}
```

手工纳入时仍会检查：

1. 是否存在股票
2. 是否被 `manual_ban`
3. 是否不可交易
4. 是否在冷却期
5. 是否基础信息缺失
6. 批量纳入上限
7. 每日纳入上限
8. 单策略容量
9. 同行业容量
10. 同概念容量

手工纳入成功后，同样进入量化，并记录生命周期事件。

## 10. 量化生命周期状态

| 状态 | `quant_enabled` | 是否参与实时主扫描 | 说明 |
|---|---:|---|---|
| `inactive` | 0 | 否 | 不属于量化管理域 |
| `trial` | 1 | 是 | 量化，允许 BUY，但仓位较轻 |
| `active` | 1 | 是 | 正式扫描，允许正常 BUY / SELL / HOLD |
| `exit_only` | 1 | 是 | 只出场管理，禁止新 BUY / 加仓 |
| `cooling` | 1 | 否 | 冷却，参与低频重评估 |
| `retired` | 0 | 否 | 退出自动量化，只在强候选事件触发时考虑复活 |
| `manual_paused` | 0 | 否 | 用户手工暂停，只允许用户恢复 |

## 11. 实时模拟如何使用生命周期

实时模拟主扫描只读取：

```text
quant_status in ('trial', 'active', 'exit_only')
```

也就是说：

1. 量化股票会被扫描。
2. `active` 股票会被扫描。
3. `exit_only` 股票会被扫描，但只能卖出或持有。
4. `cooling` 不参与主扫描。
5. `retired / manual_paused / inactive` 不参与主扫描。

### 11.1 exit_only 的交易保护

如果股票处于 `exit_only`，但策略又产生 BUY 或 ADD，信号中心会强制改写：

```text
BUY / ADD -> HOLD
decision_type = exit_only_blocked
```

信号解释里会标注：

```text
生命周期门控：exit_only 只出场管理，禁止新买入或加仓，转为 HOLD。
```

这样可以确保“只出场管理”不会再被技术 BUY 重新买入。

## 12. 生命周期如何自动降级

每次实时模拟产生信号后，系统会更新该股票的生命周期健康度和状态。

调用链：

```text
QuantSimEngine.analyze_candidate / analyze_positions
-> SignalCenterService.create_signal
-> QuantUniverseManager.update_after_signal
```

### 12.1 health_score

`health_score` 来自最近若干信号的滑动窗口，使用 profile 中的 `health_score_lookback_checkpoints`。

输入包括：

1. 平均 `tech_score`
2. 平均 `context_score`
3. 平均 `fusion_score`
4. 平均 `buy_strength_score`
5. 最近止损数量
6. blocked 数量

系统会把这些指标归一化为 0 到 100，再按 profile 权重计算健康度。

### 12.2 weakening_warning

以下情况会计入弱化预警：

1. 最终是 HOLD，且 `tech_score` 低于 profile 的弱化阈值
2. `fusion_score < trial_threshold`
3. 价格贴近 MA20，但 `buy_strength_score < 0.45`
4. 组合级门控判断为 `weak_buy`

弱化预警不会立刻退出，但会增加 `weakening_warning_streak`。

### 12.3 downtrend_hit

以下情况会计入下行命中：

1. 最终信号是 SELL
2. HOLD 且 `tech_score <= 0`，并且融合分低于阈值或融合分继续下降
3. 价格跌破 MA20 且 MA20 斜率不向上
4. 弱化预警连续达到阈值
5. 出现快速止损失败标记
6. blocked 连续达到阈值

下行命中会增加 `downtrend_streak`。

### 12.4 自动状态变化

当前主路径自动状态变化如下：

| 当前状态 | 条件 | 新状态 |
|---|---|---|
| `trial / active` | 有持仓，且 `health_score < exit_only_threshold` 或 `downtrend_streak` 达标 | `exit_only` |
| `trial / active` | 无持仓，且 `health_score < cooling_threshold` 且 `downtrend_streak` 达标 | `cooling` |
| `exit_only` | 持仓已清空，但没有满足恢复条件 | `cooling` |

说明：

1. 有持仓时不会直接进入 `cooling / retired`，必须先进入 `exit_only` 管理卖出。
2. 当前主扫描自动更新路径不会直接把 `exit_only` 恢复为 `active`；恢复通常通过手工恢复或新的候选事件触发。
3. `cooling` 股票会在调度周期后做低频机会性重评估，每次最多处理 5 只，按健康度低到高优先。

## 13. 手工覆盖

用户可以对单股设置手工覆盖。

API：

```text
POST /api/v1/quant/universe/actions/set-override
```

覆盖类型：

| 覆盖 | 行为 |
|---|---|
| `manual_pin` | 手工优先，不等于强制买入 |
| `manual_pause` | 进入 `manual_paused`，`quant_enabled=0` |
| `manual_ban` | 禁止自动纳入或恢复，`quant_enabled=0` |
| `none` | 清除手工覆盖 |

手工恢复：

```text
POST /api/v1/quant/universe/actions/restore-to-trial
```

只允许从以下状态恢复到 `trial`：

```text
cooling / manual_paused / retired
```

如果对 `active / trial / exit_only` 调用恢复接口，会返回非法状态错误。

## 14. UI 状态字段

发现页和研究页每行都会追加生命周期入口字段：

| 字段 | 说明 |
|---|---|
| `eligible_status` | `eligible / skipped / already_in_quant / cooling_blocked` |
| `candidate_score` | 当前生命周期候选评分 |
| `candidate_confidence` | 当前生命周期候选置信度；没有候选事件时保留发现阶段归一化置信度 |
| `source_score` | 发现阶段归一化推荐分 |
| `confidence` | 发现阶段归一化置信度 |
| `technical_confirmation_count` | 发现阶段结构化技术确认数量 |
| `lifecycle_score_diagnostics` | 分值来源、置信度来源、证据桶和缺失证据原因 |
| `blocking_reason` | 阻断原因，例如 `manual_ban`、`basic_info_missing` |
| `already_in_quant` | 是否已经在 `trial / active / exit_only` |

常见 UI 状态含义：

| 状态 | 含义 |
|---|---|
| `eligible` | 可一键纳入量化 |
| `already_in_quant` | 已在实时量化主扫描范围 |
| `cooling_blocked` | 冷却期内，暂不允许纳入 |
| `skipped / not_evaluated` | 未达标、手工模式、或尚未评估 |

## 15. API 口径

主要 API：

| API | 用途 |
|---|---|
| `GET /api/v1/quant/universe/settings` | 获取生命周期开关 |
| `POST /api/v1/quant/universe/settings` | 修改 `auto_entry_mode` 等设置 |
| `GET /api/v1/quant/universe/state` | 查询生命周期状态列表 |
| `GET /api/v1/quant/universe/overview` | 查询工作台量化概览卡片 |
| `POST /api/v1/quant/universe/actions/promote-to-trial` | 批量纳入量化 |
| `POST /api/v1/quant/universe/actions/ignore-auto-entry` | 忽略自动纳入 |
| `POST /api/v1/quant/universe/actions/set-override` | 设置手工覆盖 |
| `POST /api/v1/quant/universe/actions/restore-to-trial` | 从 cooling / manual_paused / retired 恢复到量化 |

发现 / 研究任务入口：

| API | 行为 |
|---|---|
| `POST /api/v1/discover/actions/run-strategy` | 执行发现策略，完成后自动写候选事件并按模式处理 |
| `POST /api/v1/research/actions/run-module` | 执行研究模块，完成后自动写候选事件并按模式处理 |
| `GET /api/v1/tasks/{task_id}` | 查询异步任务；发现任务的 `result.quantAutoEntry` 返回自动入池尝试、候选事件、已纳入、eligible 和 skipped 明细 |

## 16. 数据表

| 表 | 用途 |
|---|---|
| `stock_universe` | 统一股票池主表，保存成员关系和 `quant_status / quant_enabled` |
| `stock_universe_candidate_events` | 候选事件，表示某来源推荐某股票进入量化关注 |
| `stock_universe_quant_state` | 生命周期派生状态，例如 `candidate_score / health_score / streak / cooling_until` |
| `stock_universe_quant_events` | 生命周期事件流水，例如纳入量化、状态切换 |
| `quant_universe_settings` | 生命周期系统级设置 |

## 17. 典型流程示例

### 17.1 默认 confirm_first

```text
发现页运行低价擒牛
-> 输出 000001 平安银行
-> 自动写入 stock_universe
-> 自动写入 stock_universe_candidate_events
-> candidate_score >= stable.trial_threshold
-> 事件标记 eligible
-> UI 显示 eligible
-> 用户点击“纳入量化”
-> quant_status = trial, quant_enabled = 1
-> 实时模拟开始扫描该股
```

### 17.2 auto_trial

```text
研究页运行龙虎榜
-> 输出 002463 沪电股份
-> 自动写入 stock_universe
-> 自动写入 candidate event
-> candidate_score 达标
-> 未被 manual_ban / cooling / non_tradable / basic_info_missing 阻断
-> 自动 promoted_to_trial
-> UI 显示 already_in_quant
-> 实时模拟开始扫描该股
```

### 17.3 后续退出

```text
股票处于 active
-> 连续信号转弱
-> health_score 下降
-> downtrend_streak 达标
-> 如果有持仓：active -> exit_only
-> exit_only 禁止新 BUY / ADD，只允许 SELL / HOLD
-> 清仓后恢复不足：exit_only -> cooling
-> cooling 不再参与主扫描，只做低频重评估
```

## 18. 排查清单

如果发现股票没有自动进入量化，按以下顺序检查：

1. 是否真的重新运行了发现 / 研究任务，而不是只打开旧结果页。
2. `quant_universe_lifecycle_enabled` 是否为 true。
3. `auto_entry_mode` 是 `manual_only / confirm_first / auto_trial` 哪一种。
4. UI 行上 `eligible_status` 是什么。
5. `blocking_reason` 是否为：
   - `basic_info_missing`
   - `cooling_blocked`
   - `manual_ban`
   - `non_tradable`
   - `below_trial_threshold`
   - `daily_capacity_exceeded`
6. 该股票是否已经处于 `trial / active / exit_only`，如果是则不会重复创建候选事件。
7. 当前策略 profile 是否过于保守，导致 `trial_threshold` 较高。
8. 是否触发每日自动纳入容量上限。

## 19. 当前实现边界

1. 自动入池只在发现 / 研究任务执行完成后触发。
2. 旧缓存结果不会在页面 GET 时自动补写候选事件。
3. `manual_only` 会写候选事件，但不会标记 eligible，也不会进入 trial。
4. `auto_trial` 自动纳入目前检查每日总量上限；手工批量纳入会额外检查批次、单策略、行业、概念容量。
5. `exit_only` 当前主扫描自动路径更偏防守：清仓后若未满足恢复条件，会进入 `cooling`；恢复通常通过手工恢复或新的强候选事件触发。
6. 生命周期管理不会直接远程拉行情或 AI 分析；行情、技术指标和基础信息仍走统一刷新体系。
